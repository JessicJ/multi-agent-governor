# Multi-Agent Governor 证据评测协议

状态：`draft-v1`
适用范围：Python PR／代码变更的只读缺陷审查

## 1. 这份协议要证明什么

Governor 的目标不是证明“多 Agent 永远更好”，而是检验：

1. 哪些任务从 1 个 Agent 增加到 2、3、4 个后，严重缺陷发现能力确实改善；
2. 哪些可观察信号能够预测“下一个 Agent 已经没有足够边际价值”；
3. 在质量护栏成立的前提下，Governor 是否减少 Agent 调用和 Token；
4. Governor 自己的判断开销是否小于它节省的开销。

单元测试只能证明代码按既定规则运行，不能证明规则在真实任务上有效。

## 2. 首轮实验边界

- 任务形态：指定 PR／代码变更审查，不做全仓库自由审计；
- 编程语言：Python；
- 协作结构：一个主 Agent 汇总，其余 Agent 独立审查；
- Agent 类型：同模型、同工具、同基础审查说明；
- 变量：每组只改变总 Agent 数量；
- 固定组别：恰好使用 1、2、3、4 个 Agent；
- 权限：所有 Agent 只读代码；
- 验证：与 Agent 运行环境隔离的真值卡、确定性匹配和必要的人工盲审。

这里的 `total_agents` 包含主 Agent。评分程序不是 Agent，不计入 Agent 数量。

## 3. 任务集

### 3.1 工程试跑

工程试跑包含 12 个任务：

- 8 个真实历史缺陷；
- 4 个人工植入缺陷；
- 每个任务运行 1、2、3、4 Agent 四组；
- 每组重复 2 次；
- 共 96 次完整试验。

工程试跑的真值卡和触发测试随开源仓库公开，只在单次 Agent 运行时隔离。工程试跑只验证任务制作、运行、记录和评分是否正确，不能用于宣传 Governor 已经有效，也不能作为秘密保留集。

### 3.2 正式评测

正式评测至少包含 60 个任务，每组重复 3 次，共至少 720 次完整试验。

正式任务分成两批：

- 校准任务：用于确定清单式规则和阈值；
- 保留任务：规则锁定后才运行，用于检验规则是否适用于没参与规则制定的新项目。

同一个代码仓库不能同时出现在两批中。12 个工程试跑任务不进入正式结果。
正式评测的保留任务、真值卡和触发测试必须放在独立的私有评测环境中，在规则锁定前不得公开。

### 3.3 任务制作要求

每个任务必须：

- 固定仓库、基础 revision 和待审 patch；
- 建议涉及 3–10 个文件；
- 对工程试跑，在 Agent 运行时隔离缺陷答案、真实修复和触发测试；对正式保留任务，同时保持仓库外私有；
- 记录代码许可与任务来源；
- 对历史项目中的额外未知发现保留盲审入口，不能自动算误报。

历史缺陷可以从真实修复中恢复缺陷版本，再与正常改动组成待审变更。人工缺陷应覆盖边界条件、空值、权限、数据写入、并发等类型。

## 4. 真值卡与 Agent 输出

每个已知缺陷的评测真值卡至少包含：

- `defect_id`
- 文件和函数／符号；
- 标准化根因类别；
- 基于实际影响的严重度；
- 是否属于红线缺陷；
- 可选的触发测试。

Agent 必须输出结构化发现：

- `finding_id`
- 文件和函数／符号；
- 标准化根因类别；
- 影响；
- 可检查证据；
- Agent 声称的严重度。

Agent 声称的严重度只用于审计，不参与真值严重度计算。

## 5. 评分

文件、函数和根因类别均精确匹配时，可以自动认定命中。重复命中同一个缺陷只算一次，并单独记录重复数量。

无法确定的发现进入盲审，不直接算误报。盲审者不能看到该结果来自几个 Agent。盲审结果只能是：

- 命中一个已知缺陷；
- 发现了真值卡之外的有效缺陷；
- 误报。

主要质量指标：

- 严重缺陷召回率。

质量硬约束：

- 相比高 Agent 数方案，严重缺陷召回率的下降不得超过 2 个百分点；
- 误报占比的上升不得超过 3 个百分点；
- 安全、权限和数据损坏等红线漏检必须单独报告，不能被平均分掩盖。

如果样本不足以支持结论，报告状态必须是“证据不足”，不能放宽护栏。

## 6. 覆盖与停止信号

普通变更至少由一个 Agent 检查。权限、认证、支付、数据写入、并发、加密和删除等高风险变更至少由两个 Agent 独立检查。

运行时只允许使用当时可观察的信息：

- 已审查的变更文件；
- 高风险文件是否得到独立复查；
- Agent 之间是否存在未解决冲突；
- 新增且不重复的发现；
- 新增证据与上一轮的重复程度；
- Token、调用次数和耗时。

每个 Agent 报告到达后应写入一个检查点，记录当时总 Agent 数、新发现数、重复发现数、新覆盖文件、未解决冲突以及本轮新增用量。检查点只保存结构化统计，不保存完整回答。

真值卡只能用于实验评分，不能成为 Governor 的运行时输入；正式保留任务的真值还必须保持私有。

未来停止规则必须同时考虑：

1. 覆盖要求已经满足；
2. 没有未解决的实质冲突；
3. 最新 Agent 没有带来足够的新证据。

具体“足够”的数字由实验校准，本协议不预设最终停止阈值。

## 7. 成本口径

核心记录：

- 主 Agent 与所有子 Agent 的输入、输出和缓存 Token；
- 运行器单独报告的推理输出 Token（诊断项，不与输出 Token 重复相加）；
- Governor 检查点 Token；
- 模型调用次数；
- 工具调用次数；
- 实际 Agent 数；
- 端到端耗时。

`agent_input_tokens` 包含缓存输入；`cached_input_tokens` 是其中的诊断子集，计算总 Token 时不能重复相加。`governance_tokens` 只记录尚未包含在 Agent 输入／输出中的额外治理开销。

使用 Codex CLI 时，保存 `codex exec --json` 的 JSONL。其最终
`turn.completed.usage` 事件可提供输入、缓存输入、输出和推理输出 Token；用
`magov-eval codex-usage` 将其转换为本项目的用量记录。

金额不是核心指标。只有在价格可靠时才允许根据原始用量做可选换算。

所有质量和成本比较都必须包含 Governor 的自身开销：

```text
总消耗 =
主 Agent
+ 子 Agent
+ 协调与汇总
+ Governor 检查点
+ 验证调用
```

## 8. 本地记录与隐私

- 运行记录默认只保存在本地；
- 物化后的 Agent 目录不得包含 `.git`、准确修复 revision 或指向目录外的
  符号链接；物化失败必须删除半成品目录；
- 单次盲测只挂载物化目录并关闭外网访问，避免 Agent 根据公开任务编号、
  上游提交或公开真值反查答案；
- 不上传仓库代码、完整提示词或 Agent 完整回答；
- JSONL 只保存任务编号、固定实验条件、结构化发现、覆盖、用量和评分；
- 用户主动选择后才可以导出匿名统计；
- 开源项目不依赖中央遥测服务器。

`evals/runs/` 用于本地实验结果，默认被 Git 忽略。

## 9. 结果状态

评测报告必须给出以下三种状态之一：

- `pass`：质量护栏成立，并且包含治理开销后的总用量下降；
- `fail`：质量越过护栏，或者治理后没有节省总用量；
- `inconclusive`：样本或统计精度不足，无法判断。

在保留任务完成并得到 `pass` 前，项目只能称为“实验性策略”，不能声称已证明无损节省成本。

## 10. 第一阶段不做什么

- 不启动或调度 Agent；
- 不选择异构 Agent；
- 不训练黑盒预测模型；
- 不把模型自报置信度当成证据；
- 不根据 12 个试跑任务修改并宣传最终策略；
- 不改写当前策略权重或写死最终停止阈值。
